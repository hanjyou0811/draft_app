# 後から変更するための境界

この初版では、将来の機能を先に実装する代わりに、変更が広がる場所を限定する。

## 変更の対応表

| 変更したいこと | 主に変更する場所 | 維持したいもの |
|---|---|---|
| 抽選を手動操作にする、順番指名を追加する | domain、共有の状態型、該当画面 | 保存・通信アダプター |
| SQLiteをPostgreSQLや外部DBにする | repositoryの実装、起動時の組み立て | 純粋なドラフトルールとそのテスト |
| WebSocketをSSEや外部配信サービスにする | サーバーの配信部分、useRoom | HTTP操作、公開ビュー、ドラフトルール |
| 見た目や画面構成を変更する | src/components、styles | APIとドメイン |
| 候補一覧を複数会議で再利用する | 独立したテーブル保存、会議作成処理、管理画面 | 開始時に確定した候補に対する指名処理 |
| アカウントを導入する | 認証、参加資格の解決、入室UI | 参加者IDを入力にするドラフトルール |

「維持したい」は無変更を保証する意味ではない。公開データ形式やルール自体を変える場合は、関連する契約とテストも更新する。

## 守る契約

- ドメインは外部I/Oを行わず、入力の状態から次の状態を計算する。
- 抽選の乱数は引数で渡す。本番はサーバーの乱数、テストは決定的な値を使う。
- Repositoryは非同期契約。ローカルSQLiteの同期APIをドメインに漏らさない。
- 保存成功後の状態だけを配信する。公開ビューを作ってから配信し、内部状態をそのまま送らない。
- 1回の操作を状態の更新番号とともに原子的に保存する。別DBへ移してもこの条件を守る。
- 接続は通知の経路であり、正本ではない。復帰時には保存済みの最新状態を読む。

## 最小構成の代償

初版は単一プロセスで会議ごとの操作を直列化する。複数プロセスへ増やす場合は、保存競合の再試行、プロセス間通知、接続先の違いを考慮する必要がある。Repositoryを交換するだけで分散構成が完成するわけではない。

SQLiteでは会議の集約状態を1レコードとして保存する。抽選・獲得・次の巡を一括で確定しやすい一方、参加者や候補を横断する検索には不向き。検索機能が必要になったら正規化したテーブルや読み取り専用の索引を検討する。

保存形式にはバージョンを持たせる。既存の会議データがある状態で形式を変える場合は、移行処理と移行テストを追加する。未知の形式を黙って読み替えない。

参加トークンはブラウザ単位。アカウントも本人復旧手段もないため、ブラウザの保存データを消すと同じ参加者に復帰できない。アカウント導入時は参加者と本人の関係を保存する設計へ変更する。
